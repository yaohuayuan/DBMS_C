\chapter{事务、并发与恢复实验}
\label{chap:tx-recovery}

\section{实验目的}
\label{sec:tx-purpose}

本章用于理解 DBMS\_C 中事务层的基本职责。事务并不是单独完成读写的模块，它会把文件层、日志层、缓冲区层、并发控制层和恢复层组织在一起，对上层提供相对统一的读写入口。

本章当前已经完成三个基础阶段：5A 验证 \codepath{Transaction} 如何通过 \codepath{BufferList} 使用 \codepath{BufferManager}，并在提交时把修改写回到底层文件；5B 验证 \codepath{LockTable} 和 \codepath{ConCurrencyManager} 的基础加锁与释放行为；5C 验证 \codepath{RecoveryManager} 通过旧值日志完成最小整数回滚。死锁检测和崩溃恢复属于后续扩展内容，本章只保留边界说明，不提前展开。

\section{模块作用}
\label{sec:tx-role}

\codepath{tx/} 模块位于查询执行、记录管理和底层缓冲区管理之间。上层模块不需要直接操作每一个 \codepath{Buffer}，而是可以通过事务接口 pin 块、读取页内数据、写入页内数据、提交或回滚事务。

在当前实现中，\codepath{Transaction} 初始化时会创建三个重要的协作对象：\codepath{RecoveryManager}、\codepath{ConCurrencyManager} 和 \codepath{BufferList}。其中 \codepath{BufferList} 记录当前事务已经 pin 的块和对应 Buffer，使事务可以在后续读写时找到已经固定的缓冲页。

\section{关键代码讲解}
\label{sec:tx-code}

第一段代码来自 \codepath{tx/Transaction.c} 的 \apiname{TransactionInit}。事务初始化时会保存文件管理器和缓冲区管理器，并创建恢复管理器、并发管理器和 BufferList。

\begin{dbcode}{TransactionInit 初始化事务协作对象}
Transaction* TransactionInit(FileManager*fileManager,
                             LogManager*logManager,
                             BufferManager*bufferManager){
    Transaction *transaction = malloc(sizeof (Transaction));
    transaction->txNum = TransactionNextTxNumber(transaction);
    transaction->fileManager = fileManager;
    transaction->bufferManager = bufferManager;
    transaction->recoveryManager =
        RecoveryManagerInit(transaction, transaction->txNum,
                            logManager, bufferManager);
    transaction->conCurrencyManager = ConCurrencyManagerInit();
    transaction->bufferList = BufferListInit(bufferManager);
    transaction->code = TX_TRANSACTION_RUN;
    return transaction;
}
\end{dbcode}

第二段代码来自 \codepath{tx/BufferList.c} 的 \apiname{BufferListPin}。它向 BufferManager 申请目标块对应的 Buffer，并把块到 Buffer 的映射记录到当前事务的 BufferList 中。

\begin{dbcode}{BufferListPin 记录事务 pin 的块}
void BufferListPin(BufferList *bufferList, BlockID *blockId){
    Buffer *buffer = BufferManagerPin(bufferList->bufferManager, blockId);
    BufferTEMP *bufferTemp = BufferTEMPInit();
    bufferTemp->buffer = buffer;
    map_set(bufferList->buffers,
            CStringGetPtr(BlockID2CString(blockId)),
            *bufferTemp);

    BlockIDNode *blockIdNode = bufferList->pin;
    while(blockIdNode->next != NULL){
        blockIdNode = blockIdNode->next;
    }
    BlockIDNode *NewBlockIDNode = malloc(sizeof(BlockIDNode));
    NewBlockIDNode->blockId = BlockIDInit(blockId->fileName,
                                          blockId->BlockID);
    NewBlockIDNode->next = NULL;
    blockIdNode->next = NewBlockIDNode;
}
\end{dbcode}

第三段代码来自 \codepath{tx/Transaction.c} 的 \apiname{TransactionSetInt}。写入前事务会申请写锁，随后从 BufferList 找到 Buffer，把整数写入 Page，并把 Buffer 标记为本事务修改过。

\begin{dbcode}{TransactionSetInt 写入页内整数}
void TransactionSetInt(Transaction*transaction, BlockID *blockId,
                       int offset, int val, bool okToLog){
    ConCurrencyManagerXLock(transaction->conCurrencyManager, blockId);
    Buffer *buffer = BufferListGetBuffer(transaction->bufferList, blockId);
    int lsn = -1;
    if(okToLog){
        lsn = RecoverySetInt(transaction->recoveryManager,
                             buffer, offset, val);
    }
    Page *page = buffer->page;
    PageSetInt(page, offset, val);
    BufferSetModified(buffer, transaction->txNum, lsn);
}
\end{dbcode}

第四段代码来自 \codepath{tx/Transaction.c} 的 \apiname{TransactionCommit}。提交时先走恢复管理器的提交入口，再释放锁和当前事务 pin 过的 Buffer，最后把事务状态改为已提交。

\begin{dbcode}{TransactionCommit 提交事务}
void TransactionCommit(Transaction*transaction){
    TransactionTraceCommit(transaction);
    RecoveryCommit(transaction->recoveryManager);
    printf("transaction %d commit\n", transaction->txNum);
    ConCurrencyManagerRelease(transaction->conCurrencyManager);
    BufferListUnpinAll(transaction->bufferList);
    transaction->code = TX_TRANSACTION_COMMIT;
}
\end{dbcode}

\section{5B 并发锁基础实验}
\label{sec:tx-concurrency-basic}

事务层在读写块之前会先进入并发控制模块。当前实现中，读操作通过 \apiname{ConCurrencyManagerSLock} 获取共享锁，写操作通过 \apiname{ConCurrencyManagerXLock} 获取排他锁；提交或回滚时，\apiname{ConCurrencyManagerRelease} 会释放当前事务管理器记录的所有锁。

\codepath{LockTable} 是全局锁表，内部用 \codepath{map\_int\_t} 记录每个 \codepath{BlockID} 对应的锁状态。当前约定是：值为正数表示共享锁数量，值为 \codepath{-1} 表示排他锁，值不存在或查询为 0 表示没有锁。\codepath{ConCurrencyManager} 则是事务侧的锁管理器，它用 \codepath{map\_str\_t} 记录当前事务已经持有的锁类型，例如 \codepath{"S"} 或 \codepath{"X"}。

\section{5C 恢复与回滚基础实验}
\label{sec:tx-recovery-basic}

恢复管理模块负责在事务修改数据前记录足够的信息，使事务回滚时可以把被修改的数据恢复到旧值。当前实现中，\codepath{TransactionSetInt} 和 \codepath{TransactionSetString} 在 \codepath{okToLog} 为 true 时，会调用 \codepath{RecoverySetInt} 或 \codepath{RecoverySetString} 记录修改前的旧值；随后才真正修改缓冲页。

\codepath{RecoveryManager} 位于事务层内部，连接 \codepath{LogManager} 与 \codepath{BufferManager}。日志记录的具体格式由 \codepath{LogRecord} 负责解析和执行 undo。图 \ref{fig:tx-recovery-objects} 展示了当前 rollback 基础路径中几个对象之间的关系。

\begin{figure}[htbp]
  \centering
  \resizebox{0.92\textwidth}{!}{%
  \begin{tikzpicture}[node distance=9mm and 13mm]
    \node[dblevel] (tx) {Transaction};
    \node[dbnode, right=of tx] (rm) {RecoveryManager\\commit / rollback / set old value};
    \node[dbnode, right=of rm] (log) {LogManager\\append / iterator / flush};
    \node[dbnode, below=of rm] (buf) {BufferManager\\flush modified buffers};
    \node[dbsubnode, below=of log] (record) {LogRecord\\START / SETINT / COMMIT / ROLLBACK};
    \node[dbsubnode, below=of buf] (page) {Buffer + Page\\current data value};

    \draw[dbarrow] (tx) -- (rm);
    \draw[dbarrow] (rm) -- (log);
    \draw[dbdown] (rm) -- (buf);
    \draw[dbdown] (log) -- (record);

  \end{tikzpicture}}
  \caption{Transaction、RecoveryManager、LogManager 与 BufferManager 的关系}
  \label{fig:tx-recovery-objects}
\end{figure}

为什么要在修改前记录旧值？因为 rollback 的核心不是“撤销函数调用”，而是把数据页恢复成修改之前的内容。以整数写入为例，\apiname{RecoverySetInt} 会先从当前 \codepath{Buffer->page} 读出旧值，再调用 \apiname{SetIntRecordWriteToLog} 把事务号、文件块、偏移量和旧值写入日志。图 \ref{fig:tx-setint-log} 展示了这个记录过程。

rollback 时，\apiname{RecoveryDoRollback} 会通过日志迭代器从后向前读取日志，找到当前事务的日志记录。如果遇到 \codepath{SETINT} 记录，就调用该记录的 undo 函数，把记录中的旧值写回原来的 \codepath{BlockID} 和 offset；如果遇到当前事务的 \codepath{START} 记录，说明这个事务的回滚扫描结束。图 \ref{fig:tx-rollback-flow} 展示了这条基础链路。

本轮新增的恢复基础测试文件为：
\begin{itemize}
  \item \codepath{test/tx/RecoveryBasicTest.c}
\end{itemize}

该测试使用独立数据库目录、独立数据文件和日志文件。测试流程是：先启动一个事务写入初始整数并提交；再启动第二个事务读取旧值、使用 \codepath{TransactionSetInt(..., true)} 修改该整数；随后调用 \codepath{TransactionRollback}；最后从文件块读回并断言值恢复为旧值。

单独运行 5C 测试可以使用：

\begin{dbcode}[listing options={language=bash}]{运行恢复与回滚基础测试}
ctest --test-dir build --output-on-failure -R Recovery
\end{dbcode}

本轮没有测试字符串回滚、多事务交错和崩溃恢复。字符串日志路径在当前实现中涉及字符串生命周期和记录长度细节，适合单独补测试；多事务交错会同时牵涉锁、日志顺序和缓冲区替换；崩溃恢复需要重新打开数据库环境并验证未完成事务的 undo 结果，应作为后续更完整的恢复实验推进。

\section{运行与观察}
\label{sec:tx-run-observe}

本章的建议观察顺序如下：

\begin{enumerate}
  \item 运行 \codepath{ctest --test-dir build --output-on-failure -R Transaction}，确认事务基础测试通过。
  \item 运行 \codepath{ctest --test-dir build --output-on-failure -R Concurrency}，确认并发锁基础测试通过。
  \item 运行 \codepath{ctest --test-dir build --output-on-failure -R Recovery}，确认恢复与回滚基础测试通过。
  \item 观察 \codepath{TransactionInit} 是否为事务创建必要的协作对象。
  \item 观察 pin/unpin 前后 \codepath{TransactionAvailableBuffs} 的变化，理解事务如何占用和释放 Buffer。
  \item 观察 \codepath{TransactionSetInt} 写入后，提交是否能让 \codepath{FileManagerRead} 从文件块中读回相同整数。
  \item 观察 \codepath{LockTable} 中 S 锁、X 锁的数值表示，以及 \codepath{ConCurrencyManagerRelease} 如何清空本地锁记录。
  \item 观察 \codepath{TransactionRollback} 是否能借助 SETINT 旧值日志恢复修改前的整数。
  \item 注意本章当前没有断言 DeadlockDetector 和崩溃恢复，这些内容必须等对应测试补齐后再写入实验正文。
\end{enumerate}

\section{思考题}
\label{sec:tx-questions}

\begin{enumerate}
  \item 为什么事务层不直接读写文件，而是通过 BufferManager 和 BufferList 间接访问 Page？
  \item Transaction 为什么需要同时持有 ConcurrencyManager 和 RecoveryManager？
  \item 如果事务提交时没有释放已经 pin 的 Buffer，后续模块可能遇到什么问题？
  \item 为什么回滚测试不能只检查 TransactionRollback 是否被调用，而要结合日志和旧值恢复结果来验证？
\end{enumerate}
